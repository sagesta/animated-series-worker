# Architecture and product decisions

Decisions are locked for the current baseline. A reversal requires an entry describing the new evidence, affected requirements, migration, compatibility impact, tests, documentation, and rollback.

| ID | Status | Decision | Reason | Revisit when |
| --- | --- | --- | --- | --- |
| D-001 | Accepted | Keep this studio in its own Git repository and consume `shuohao-skills` as a pinned submodule. | Ordinary upstream pulls cannot overwrite custom work or silently alter production behavior. | The upstream project publishes a stable package/API with equivalent pinning and compatibility guarantees. |
| D-002 | Accepted | Never edit the vendored upstream checkout. Adapt through a studio-owned boundary. | Preserves clean upgrades, attribution, rollback, and upstream self-containment. | Never for ordinary features; only a documented emergency fork could supersede this. |
| D-003 | Accepted | Use a local-first Windows desktop app built with Electron, React, and TypeScript. | It supports a single installer, Node integration with existing scripts, local files, credential-vault access, and a non-technical interface. | A packaged local web app proves materially simpler without weakening file, secret, or process control. |
| D-004 | Accepted | Use SQLite as a rebuildable local index; files and versioned manifests remain the creative source of truth. | Transactional queues and dependencies need a database, while portable files prevent lock-in and aid recovery. | Scale or collaboration requires a server database. |
| D-005 | Accepted | Use LTX-2.5 as the only version-1 generative video engine; do not install or operate Wan. | It covers the intended stylized motion and audio-conditioned production path. Targeted LatentSync mouth repair is a bounded post-process, not another video-generation engine. Fewer generation engines reduce setup and user confusion. | The locked pilot shows an unacceptable shot class that LTX cannot handle, or licensing/hardware changes make it unsuitable. |
| D-006 | Accepted | Keep a versioned `VideoEngine` interface even though only LTX is installed. | A future engine can be added without contaminating canonical story and continuity data. | Never remove; it is a low-cost boundary. |
| D-007 | Accepted | Use Qwen-Image and Qwen-Image-Edit as the initial image family. | Official releases provide generation, editing, multiple-image conditioning, improved consistency, ComfyUI support, and Apache-2.0 licensing. | The character-board benchmark fails or a better commercially usable model wins the locked test pack. |
| D-008 | Accepted | Use Qwen3-TTS as the initial TTS family and save reusable, rights-cleared voice conditioning. | It supports voice design, controlled speech, reusable voice-clone prompts, multiple languages, and Apache-2.0 licensing. | Voice consistency, pronunciation, language, performance, or license gates fail. |
| D-009 | Accepted | Generate recurring dialogue audio first, approve it, and then condition video on that exact audio. | The voice must not be reinvented independently by each video generation. | A validated joint model proves equally controllable and preserves locked character voice identity. |
| D-010 | Accepted | Use RunPod as the first provider through a `GPUProvider` interface. | Templates, REST lifecycle control, persistent network volumes, and temporary GPUs match the one-click requirement. | Availability, support, security, or measured cost fails; the provider interface then permits replacement. |
| D-011 | Accepted | Use temporary Pods with a persistent network model cache for version 1, not serverless first. | Large models, debugging, workflow visibility, and predictable sessions are simpler initially. Automatic creation and termination still hide infrastructure from the user. | Stable benchmarks show serverless cold starts and pricing are better for this workload. |
| D-012 | Accepted | The remote worker is a versioned Docker image with an authenticated gateway; ComfyUI binds only to loopback. | Reproducible setup and a narrow security boundary are safer than exposing ComfyUI directly. | The inference layer no longer uses ComfyUI. The authenticated gateway remains required. |
| D-013 | Accepted | Use human approval gates before character, voice, style, storyboard, bulk generation, and final release locks. | Creative errors become far more expensive when multiplied across hundreds of shots. | Never remove globally; individual gates may gain safe batch approval. |
| D-014 | Accepted | Use hybrid editorial construction rather than generating every final second. | Stylized animation benefits from controlled holds, loops, parallax, reactions, and reusable material; this reduces cost and improves continuity. | A future model makes full-duration generation demonstrably cheaper and more consistent. |
| D-015 | Accepted | Treat series and one-off films as the same `Project` aggregate with different organization. | Both need the same bibles, shot jobs, approvals, continuity, costs, and exports. | Their workflows diverge enough to require separate products. |
| D-016 | Accepted | Do not automatically publish to YouTube in version 1. Produce a verified upload package instead. | Public publishing has account, title, rights, timing, and irreversible audience consequences outside the generation problem. | A separate reviewed publishing feature is approved. |
| D-017 | Accepted | Default delivery is 1920×1080, 16:9, 24 fps, SDR BT.709, H.264 video, AAC-LC 48 kHz stereo, with captions. | It is broadly compatible and matches the planned cinematic animation cadence and YouTube guidance. | A project deliberately selects another delivery profile and passes QC. |
| D-018 | Accepted | Model, workflow, adapter, schema, and upstream updates apply prospectively; existing approved outputs keep their original manifests. | Reproducibility requires history not to mutate when defaults improve. | Never; a new render is a new take/version. |
| D-019 | Accepted | Documentation changes are part of the same feature or fix, with no code-only behavioral hotfix exception. | The user explicitly requires future fixes to keep the plan accurate, and drift is most dangerous during emergency work. | Never; an emergency rollback can precede the completed incident change, but closure still includes docs and tests. |
| D-020 | Accepted | Use the Electron-bundled `node:sqlite` implementation for the Phase 1 local catalog and per-project databases instead of a separately compiled SQLite add-on. | It keeps SQLite inside the pinned desktop runtime, avoids native add-on rebuild/installer fragility, and still provides synchronous transactions for infrequent project lifecycle operations. | The runtime API changes incompatibly, packaging/integrity tests fail, or measured workload needs require another maintained driver. |
| D-021 | Accepted | Store the RunPod key as an encrypted binary outside all project folders using Electron `safeStorage`; on Windows its key protection is provided by DPAPI. | It uses the pinned desktop runtime and operating-system protection without a fragile native keychain add-on, never returns the secret to the renderer after submission, and keeps it out of projects, exports, logs, Git, and support data. | Electron changes the security semantics incompatibly, Windows protection is unavailable, or a maintained credential-manager adapter provides materially stronger isolation without packaging risk. |
| D-022 | Superseded | The earlier design selected a differently named RunPod REST v2 management surface. | The current official Pod management reference and response contracts use `rest.runpod.io/v1`, while GPU catalogue reads use `api.runpod.io/v2`; D-048 records the implemented split. | Historical only. |
| D-023 | Accepted | Add provider-neutral writing adapters, with OpenAI Responses and Anthropic Messages as the first bring-your-own-key providers; no provider conversation is the canonical story record. | The creator can choose a writing service without locking projects to it, while structured project bibles/scripts remain locally versioned and portable. Separate provider keys use the same protected vault boundary as RunPod and are never exposed to skills or project files. | A provider retires the selected API, fails the writing benchmark, or a local writing engine meets the same quality and usability gates. |
| D-024 | Accepted | Treat external creative skills as versioned, permissioned capabilities with declared task kinds, inputs, outputs, and validation. Installing or enabling a skill does not count as using it: every applicable required skill must produce an execution receipt, and every result must show the skills actually used. | A visible execution plan and immutable provenance prevent attached skills from becoming decorative prompts that the model silently ignores. Declarative skills are the default; executable code, custom nodes, and remote tools require stronger review and isolation. | A safer interoperable skill standard provides equivalent routing, enforcement, provenance, permissions, and rollback. |
| D-025 | Accepted | Images, audio, and videos are viewed, compared, approved, and edited inside Animated Series Studio. ComfyUI runs headlessly as a loopback-only worker engine and is not a required user interface. | ComfyUI officially supports programmatic workflow submission, progress events, and output download without opening its browser UI. Keeping review in the studio provides a non-technical workflow, local project history, and a narrow remote security boundary. | ComfyUI is replaced as an engine, or a future embedded interface passes the same usability, provenance, and security gates. |
| D-026 | Accepted | A character's identity, visual rendering style, wardrobe, and story-state variants are separately versioned. Any style/redesign change creates a new version with explicit scope (`shot`, `scene`, `episode`, `season`, or `future project work`) and never overwrites completed work. | This permits deliberate 2D/3D-look changes, transformations, flashbacks, costume eras, and redesigns while preserving character identity, continuity, prior episodes, lineage, and cost control. | Never for destructive in-place replacement; scope options may expand after timeline/version tests. |
| D-027 | Accepted | Require a versioned timed animatic using storyboard frames and approved or clearly temporary audio before bulk video generation. | Shot timing, pacing, missing coverage, dialogue length, and episode duration are cheaper to correct before hundreds of GPU takes exist. | A validated alternative proves equally reviewable timing and dependency impact without paid final generation. |
| D-028 | Accepted | Represent pose, depth, edge, segmentation, masks, motion tracks, start/end frames, and reference clips as engine-neutral versioned control assets. Compile them only into benchmark-approved Qwen/LTX workflows. | It provides rich shot control without making community node IDs or one model's graph the canonical production record. | A future control standard replaces the internal schema while preserving migration and lineage. |
| D-029 | Accepted | Disable runtime ComfyUI Manager installation and arbitrary node/model/package updates in production workers. Dependencies are baked into a pinned worker image and promoted only after security, compatibility, GPU, and rollback tests. | “Install missing nodes” is convenient for experimentation but can change dependencies, break working graphs, expand attack surface, and spend GPU time unpredictably. | Never for an authorized production session; a separate disposable research worker may be approved with no project secrets or production promotion rights. |
| D-030 | Accepted | Use speech recognition only as a QC comparison against the approved script/audio, never as the canonical script or caption source for generated productions. | The written line and approved voice take are intentional creative sources; ASR can reveal omissions or unintelligibility but can also misrecognize valid performance. | A future workflow imports third-party recorded material whose transcript must first be established and reviewed. |
| D-031 | Accepted | Keep project-scoped character/style LoRA or equivalent adaptation optional and benchmark-gated rather than mandatory. | Multi-reference Qwen editing may be sufficient; training adds dataset rights, cost, storage, overfitting, compatibility, and rollback obligations. | The locked consistency benchmark repeatedly proves adaptation is required for the intended series style. |
| D-032 | Accepted | Keep recurring dialogue in Qwen3-TTS masters and treat generated ambience/effects/foley as separate versioned layers. LTX audio adapters are enabled only for exact validated model compatibility. | Sound generation should enrich scenes without reinventing voices or silently mixing LTX-2.3-only adapters into the LTX-2.5 worker. | A compatible model family passes dialogue identity, effects, rights, cost, and separation tests. |
| D-033 | Accepted | Automated identity, motion, flicker, lip-sync, and speech checks produce review evidence and warnings only; humans retain creative approval and release authority. | Metrics are useful for finding likely defects but cannot reliably judge stylization, intentional exaggeration, acting, or narrative context. | Never remove human release authority; low-risk batch triage may improve after audited evidence. |
| D-034 | Accepted | The studio orchestrator remains the production source of truth; n8n, ComfyUI graphs, or exported Python loops are not the version-1 job database or required user interface. | One durable scheduler must own approvals, dependencies, idempotency, retries, costs, local verification, and recovery. Duplicating that authority creates conflicting state and secret handling. | A documented external automation API can be added after the internal contracts and authorization model are stable. |
| D-035 | Accepted | Complete a backup as a separate generation containing a canonical project snapshot plus a SHA-256 inventory, and restore only through a verified temporary copy into an absent project folder. | A self-describing backup remains usable without the catalog or GPU provider; temporary generations cannot masquerade as complete, and recovery cannot overwrite the creator's surviving work. | Incremental storage is added; it must preserve self-describing generations, complete verification, and the same no-overwrite default. |
| D-036 | Accepted | Keep diagnostics structured, locally flushed, and redacted before disk; create a support artifact as explicit local JSON with no creative content/provider payloads and no automatic upload. | Plain JSON is inspectable by the creator and support tooling without adding an archive dependency, while exclusion-by-default and a second redaction/known-secret scan reduce disclosure risk. | A signed encrypted support container is required; the same preview, exclusions, redaction, explicit sharing, and no-auto-upload rules still apply. |
| D-037 | Accepted | Make project-manifest schema 2 the current write format, keep schema 1 readable, and require an explicit timestamp-bound preview plus verified backup before the v1→v2 lifecycle migration. | Archive/unarchive needs reversible lifecycle metadata, while backward reads keep old projects/backups visible and four-point rollback prevents a failed upgrade from silently stranding creative work. | A later schema adds a registry/chain; it must preserve explicit preview, pre-migration backup, stale-preview refusal, atomic activation, validation, and rollback. |
| D-038 | Accepted | Treat thumbnails, title/description/chapters, captions, credits, audience/disclosure records, and upload instructions as one versioned YouTube release package; keep automatic publishing outside version 1 and do not use a universal `SEO score`. | The reference workflow exposed a missing last-mile packaging layer, but ranking is not deterministic and public publishing has separate account/policy/irreversibility risks. A truthful, validated, copy-ready package gives the non-technical creator the benefit without surrendering release control. | A separately reviewed uploader passes OAuth, quota, private-first, duplicate/reconciliation, policy, failure, audit, and human-authorization gates. |
| D-039 | Accepted | Call unexposed title/thumbnail options `candidates`, not A/B-test results. Store hypotheses and exact hashes; recognize a winner only from imported/connected platform evidence, and never switch live metadata automatically. | Local comparison has no audience assignment or outcome evidence. Current YouTube Test & Compare evaluates simultaneous variants using watch-time share, so an invented local winner would be misleading. | A supported platform API exposes verifiable experiment creation/results and the human-controlled workflow passes security and rollback tests. |
| D-040 | Accepted | Require explicit human release attestations for child-directed audience, applicable realistic altered/synthetic-media disclosure, metadata truthfulness, originality/non-template review, rights/credits, and the full watch. Never default those declarations from project type, animation style, model output, or channel history. | Animated characters can be relevant to child-directed classification, disclosure/policy guidance changes, and a false default can create legal, platform, or monetization harm. The creator needs guidance and a recorded decision, not automated legal judgment. | Never remove creator authority; the questions and linked rules may change when official platform guidance changes. |
| D-041 | Accepted | Keep post-release analytics optional, read-only or file-imported, source/time-window labelled, and separated from human-approved recommendations. Analytics cannot rewrite locked facts, select creative work, change live metadata, or trigger spend. | Channel-relative evidence can improve future packaging and pacing, but low samples, incomparable formats, missing metrics, and optimization pressure can otherwise corrupt the series or create unsafe automation. | A bounded low-risk action is later authorized with controlled evidence, a visible preview, reversal, and retained human approval. |
| D-042 | Accepted | Add Google Gemini as the third protected writing adapter and pin a release-controlled stable model catalogue: GPT-5.6 Terra/Sol/Luna, Claude Sonnet 5/Opus 5/Haiku 4.5, and Gemini 3.7 Flash/3.5 Flash-Lite. Intersect it with the live authenticated model list and exclude preview/latest aliases or arbitrary IDs. | The creator asked to specify models. A small visible catalogue makes quality/cost intent understandable, prevents silent drift to preview or retired models, and still proves account availability before use. “Balanced” is an initial purpose label, not evidence that one model wins every writing task. | Official stable IDs retire, a controlled update passes compatibility tests, or the locked story/character/script benchmark justifies task-specific defaults. |
| D-043 | Accepted | Store Audience & Creative Direction as immutable project-sidecar versions, not as one mutable niche field or a forced project-manifest migration. Use it as a pinned compiler input while keeping canon, character identity/style bindings, and YouTube human attestations separate. | A project needs one consistent compass across writing, upstream skills, images, voice, video, thumbnails, and release copy, but mutable global prompts would cause drift and a creative age/style choice must not become a legal or platform answer. A sidecar lets older projects open unchanged and add direction when ready. | A future schema registry moves the record while preserving every version, project isolation, exact hashes, impact preview, and the policy/creative boundary. |
| D-044 | Accepted | Do not use a silently disabled primary action to communicate missing form information. Show required asterisks and live constraints, keep the action available until real work begins, and summarize every correction in an accessible popup before any trusted operation runs. | A non-technical creator should not need to guess why an action is grey. Visible rules and one correction summary prevent accidental submissions while preserving keyboard and screen-reader guidance. | A validated accessibility pattern provides equal or better clarity; busy, duplicate, destructive, or intrinsically unavailable actions may still be disabled with a visible reason. |
| D-045 | Accepted | Use isolated LatentSync 1.6 only for targeted mouth/timing repair after approved video and dialogue, and preserve the approved audio. Do not mix LTX-2.3 Dub-It into the LTX-2.5 production baseline. | The official Dub-It guide validated LTX-2.3 while LTX-2.5 support remained in development. An isolated post-process avoids checkpoint incompatibility and keeps the main video engine decision intact. | Official LTX-2.5 lip editing passes the same animated, angle, multi-person, timing, identity, rights, runtime, and audio-preservation benchmark. |
| D-046 | Accepted | Ship only a non-billable candidate workflow pack until exact model/template/image hashes, license decisions, GPU quality/runtime tests, security/recovery tests, and provider shutdown evidence atomically promote a production pack and readiness receipt. | Local code cannot prove external model quality, licensing, image contents, or cloud termination. A fingerprinted evidence gate prevents a checkbox or stale receipt from enabling spend. | Never weaken; the evidence format may evolve with a migration and equivalent or stronger verification. |
| D-047 | Accepted | Assign one GPU to one production job. Two or three GPUs mean independent compatible jobs running concurrently under one saved combined limit. | Current image, voice, and short-video workflows do not safely make one shot two or three times faster by adding unrelated GPUs; independent job concurrency provides predictable isolation, cost, and recovery. | A qualified distributed workflow proves deterministic splitting, cost benefit, recovery, and unchanged creative output. |
| D-048 | Accepted | Use the current official RunPod Pod management REST base `https://rest.runpod.io/v1` for list/get/create/start/stop/delete and the catalogue base `https://api.runpod.io/v2` for GPU inventory. Reconcile mutations by the studio lease environment ID. | This matches the implemented official endpoint contracts and prevents an uncertain create response from producing a duplicate paid Pod. | RunPod changes the official contracts or a replacement provider adapter is qualified. |
| D-049 | Accepted | Render editorial, captions, deterministic thumbnails, technical checks, and the final manual upload package locally with FFmpeg/file operations; do not keep a GPU active for those stages. | These operations are predictable on the creator workstation, preserve local authority, reduce GPU cost, and do not require ComfyUI. | A remote option proves necessary for a measured local performance limit while retaining exact approval, cost, privacy, and recovery controls. |
| D-050 | Accepted | Offer one reusable project-aware idea assistant across applicable creative and planning fields, using the existing protected provider, context-preview, declarative-skill, paid-confirmation, and proposal-lineage path. Keep secrets, numeric evidence, source transcripts, approvals, rights/policy attestations, spend, canon, GPU starts, and publishing outside its write authority. | A non-technical creator benefits from contextual starting points throughout production, but a model-generated suggestion is not evidence, consent, approval, a platform declaration, or authority to spend or publish. Reusing one governed proposal path prevents hidden provider calls and inconsistent skill use. | A specific field receives a separately reviewed typed automation contract with equal or stronger context, evidence, human-review, audit, privacy, and rollback controls. |
| D-051 | Accepted | Make Creator Mode the default experience: accept an idea or script with minimal setup, derive the next incomplete stage from durable canon/media state, attach approved context and compatible skills automatically, keep one stage-level review/approval gate, and place technical rooms behind an optional Advanced Studio toggle. Preserve separate text-billing disclosure and GPU estimate/start approvals. | The primary user is non-technical and should make creative decisions rather than manually wire providers, canon revisions, rooms, workflow IDs, or GPU infrastructure. Durable stage derivation and proposal-first approval provide useful automation without hidden spend or unreviewed creative authority. | Representative-user testing proves a different information architecture is clearer while retaining equal or stronger recovery, audit, approval, cost, accessibility, and expert-control boundaries. |
| D-052 | Accepted | Build, qualify, and promote the normal core generation worker independently from advanced profiles. Do not include the optional LTX adaptation trainer in the core image; advanced control, native-audio, foley, and adaptation candidates remain locked until separately packaged and qualified. | The trainer added a large isolated CUDA/Python environment and an unrelated 80 GB/R595 gate to every ordinary image, voice, video, and lip-repair worker even though adaptation is optional and benchmark-gated. Profile-specific immutable images preserve reproducibility while keeping the first working path smaller and independently releasable. | A measured workload proves one combined image is materially simpler and cheaper without delaying core qualification, or a shared runtime safely eliminates the size/driver coupling. |
| D-053 | Accepted | Canonical worker releases are keyless-signed only by the manual `sign-worker-image.yml` workflow from `main`, using GitHub OIDC identity `https://github.com/sagesta/animated-series-worker/.github/workflows/sign-worker-image.yml@refs/heads/main`, issuer `https://token.actions.githubusercontent.com`, the protected `worker-signing` environment, and a fixed GHCR package name. The workflow must validate the immutable manifest digest and expected config digest, use commit-pinned actions, and verify its own signature. | A personal keyless signature proves artifact integrity but does not provide a stable organization-controlled identity. A workflow-path/ref identity is reproducible, supports an exact verification policy, needs no long-lived signing key, and cannot silently sign another registry package. | Replace only with an equally narrow organization-owned hardware/KMS or reusable-workflow identity that passes key custody, least privilege, environment approval, rollback, and exact verification-policy review. |

## Open implementation selections

These choices must be resolved by the named phase rather than guessed during coding:

| ID | Decision needed | Resolution gate |
| --- | --- | --- |
| O-001 | Exact compatible 48GB/80GB GPU allowlist and preferred order | Phase 0 benchmark on current provider inventory |
| O-002 | Exact Qwen image checkpoint, quantization, and ComfyUI workflow | Character-consistency benchmark |
| O-003 | Exact LTX checkpoints, precision, draft/final dimensions, and workflow parameters | LTX 20-shot benchmark |
| O-004 | Local versus remote default for Qwen3-TTS on the user's actual computer | Voice benchmark and local hardware probe |
| O-005 | Supported external-editor interchange format in version 1 | Editorial spike before Phase 7 |
| O-006 | Music and effects source/library | Rights and workflow review before full pilot episode |
| O-007 | Task-specific default among the controlled OpenAI/Anthropic/Gemini catalogue and exact versioned quality/cost profiles | Locked story/character/script benchmark using current provider models and prices |
| O-008 | First external-skill interchange set: studio declarative package, compatible Agent Skill package, and optional MCP tool bridge | Security/compatibility spike before skill installation is enabled |
| O-009 | Exact version-1 YouTube performance import formats and whether a read-only OAuth connector ships in the first production release | Analytics/security spike before FR-064 implementation |
| O-010 | Whether a post-version-1 connector may upload private drafts, schedule reviewed videos, manage playlists, or only hand off to YouTube Studio | Separate publishing product/security review after version-1 release-package acceptance |
